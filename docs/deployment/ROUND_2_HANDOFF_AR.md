# تسليم الجولة الثانية لموظف الاستضافة - Nasbia

هذا مرجع النشر اليدوي للجولة الثانية، ويحل محل خطوات الترقية وأرقام النسخة الخاصة بتسليم 2026-11-09. الهدف **تطبيق Nasbia في جذر `Moha225121/Afhamha_Wa_Fahmni_sis`**؛ مجلد `nasr-al-daem-school` تطبيق مدرسة أخرى ولا يدخل هذا النشر. مرجع البداية البرمجي `1756cc4bf1019561c6caded736819cb3d62a81b7`، أما PR وcommit المرشح المختبر فتؤخذ من [تقرير القبول الحالي](../qa/ROUND_2_ACCEPTANCE_AR.md)، وcommit الدمج النهائي من PR المدمج وتسليم المالك، ولا تستنتج من أسماء الحزم القديمة.

**النشر يدوي لدى موظف الاستضافة فقط.** لا تسجل هذه الوثيقة تنفيذًا على الموقع: `MANUAL DEPLOYMENT PENDING` و`PRODUCTION ACCEPTANCE PENDING`. حالة التنفيذ والاختبارات وCI والدمج موثقة منفصلة في تقرير القبول. لا تعني نتائج الاختبار المحلي تحديث الموقع أو وصول Push إلى هاتف أو نجاح Gemini الحي.

## محتوى الإصدار ومتطلباته

يتضمن الإصدار إصلاحات العرض والتصحيح والنتائج، وحماية الحذف وإجراءات التعطيل/الأرشفة، والفلاتر والبطاقات، وتوقيت الإعلانات، وفحص أهلية الإشعار قبل إرسال المهمة، وحفظ محاولة رفع الدرس عند انقطاع الاتصال. لا توجد حزم جديدة أو تعديلات لازمة على ملفات قفل الاعتمادات. يلزم **نشر المصدر والأصول المطابقة وبناء Vite** لأن JavaScript الخاص بتفعيل الإشعارات تغير، كما يلزم ملف `public/js/teacher-lesson-save.js` مع قالب الدرس المطابق. لا تكفِ نسخ PHP وحدها.

الترحيلان الجديدان إضافيان:

| الترتيب | الملف | الأثر |
|---|---|---|
| 1 | `2026_11_11_000001_add_fcm_event_cancellation.php` | عمودا `cancelled_at` و`cancellation_reason` قابلان للفراغ في أحداث FCM؛ يحفظان إلغاء التوصيل دون حذف التاريخ أو الادعاء بأنه أُرسل |
| 2 | `2026_11_11_000002_create_lesson_save_requests.php` | جدول إيصالات طلب حفظ تعديل الدرس، بمفتاح طلب فريد وروابط المعلم والدرس؛ يمنع تكرار المرفقات عند إعادة طلب فقد رده |

لا ترحيل يعيد كتابة الدرجات أو الرسائل أو الالتزامات المالية أو أوقات الإعلانات القديمة. لا تُنسخ بيانات أو شعار أو صفوف المدرسة الأخرى. `APP_DISPLAY_TIMEZONE` إعداد قائم، افتراضيه `Africa/Tripoli`، ويستخدم الآن أيضًا لإدخال/عرض وقت إعلان الإدارة؛ التخزين والجدولة الداخلية يبقيان UTC. نموذج مواعيد نشر **النتائج** ما زال يسمي UTC صراحة. لا تضف ساعتين يدويًا إلى قاعدة البيانات.

## ترتيب النشر اليدوي

1. طابق المستودع والـcommit النهائي مع تقرير القبول، ثم وثّق بنية الاستضافة الفعلية ومسار الإصدار ومستخدم التشغيل وdocument root إلى `public/` وأسماء خدمات PHP والعمال والمجدول. راجع وجهة قاعدة البيانات بعد أولوية `DB_URL`. لا تعتمد على مسار أو اسم خدمة تاريخي. يجب أن يقارن المسؤول مخطط الموقع الحالي بأساس الجولة؛ الاختبار المحلي بدأ من **44 migration** وطبّق الجديدتين للوصول إلى **46**. هذا عدد الأساس المختبر، وليس إذنًا لتجاهل ترحيل ناقص أو زائد في الموقع.

2. خذ نسخة احتياطية متسقة للقاعدة والملفات العامة والخاصة، وتحقق من إمكانية استعادتها في بيئة منفصلة. احتفظ بـ`.env` و**APP_KEY الحالي** وملفات المستخدمين وملف حساب الخدمة السري خارج Git/public. احتفظ بالإصدار السابق وأصوله. أوقف قبول الكتابات أثناء نافذة تبديل المخطط والنسخة وفق إجراء الاستضافة المعتمد، وأوقف العامل والمجدول مؤقتًا بآلية التشغيل الفعلية حتى لا يعالجا jobs بشيفرة ومخطط مختلفين. لا توقف أو تعيد أي خدمة باسم تخميني.

3. جهّز مجلد إصدار جديد غير نشط من المصدر المحدد، مع ربط التخزين الدائم الحالي بدل استبداله بمجلد storage فارغ. من جذر هذا الإصدار، استخدم أوامر الاعتمادات القائمة دون تحديث ملفات القفل:

```bash
composer install --no-dev --prefer-dist --no-interaction --no-scripts --no-plugins --optimize-autoloader
composer --no-plugins check-platform-reqs --no-dev
npm ci --ignore-scripts
php artisan package:discover --ansi
npm run build
```

تُضبط البيئة المعتمدة قبل أوامر Artisan، وقيم Firebase العامة قبل البناء. انشر `public/build/manifest.json` وجميع chunks من البناء نفسه مع الأصول العامة الحالية. لا تنسخ vendor/node_modules من Windows إلى Linux، ولا تشغّل `composer update` أو `npm update` أثناء إعداد هذا الإصدار.

4. افحص سجل الترحيلات أولًا من الإصدار الجديد وباتصال المدرسة المقصودة:

```bash
php artisan migrate:status
```

إذا كانت الترحيلات السابقة غير مكتملة، طابق الفجوة مع المصدر وتقرير النسخة الحالية قبل تفعيل الجولة؛ لا تعالجها بتصفير قاعدة أو seeder. عند مطابقة الأساس، طبّق الجديدتين بالترتيب:

```bash
php artisan migrate --path=database/migrations/2026_11_11_000001_add_fcm_event_cancellation.php --force --no-interaction
php artisan migrate --path=database/migrations/2026_11_11_000002_create_lesson_save_requests.php --force --no-interaction
php artisan migrate:status
```

إعادة `migrate` على ملف مسجل لا تعيد تطبيقه. إذا فشل أحدهما، احتفظ بالخطأ المنقح وحالة المخطط وأوقف تبديل الإصدار للتحقيق؛ لا تستخدم rollback عامًا. لا `migrate:fresh` أو `db:seed` أو `key:generate` أو سكربت تثبيت قديم على موقع قائم.

5. بعد نجاح المخطط وضبط البيئة، ابنِ cache الخاص بالإصدار الجديد:

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

بدّل الإصدار بآلية الاستضافة المعتمدة وأعد تحميل PHP/OPcache والعمليات طويلة العمر بأسمائها الفعلية. حافظ على التخزين الدائم و`public/storage` والصلاحيات وHTTPS. لا تنشر cache مطور أو ملفات البيئة التجريبية.

6. أعد العامل والمجدول بعد التحقق من أنهما يستخدمان المصدر والمخطط الجديدين. الأمر الموجود في المشروع للعامل، إذا كان اسم الصف هو `default`:

```bash
php artisan queue:work database --queue=default --sleep=3 --tries=4 --timeout=60
```

يجب أن يدير المشرف الفعلي العملية ويعيدها بعد خروجها؛ لا تشغّل نسخة ثانية فوق عامل قائم. يتطابق اتصال database queue مع اتصال قاعدة التطبيق؛ يترك `DB_QUEUE_CONNECTION` غير مضبوط أو مساويًا لاسم الاتصال الافتراضي. طابق اسم الصف مع `DB_QUEUE` إن اختلف. مهلة العامل 60 ثانية أقل من `retry_after` الافتراضي 90 ومن قفل المهمة 120؛ تحقق من دعم timeout على نظام الاستضافة ومن مخزن أقفال مشترك.

```bash
php artisan queue:restart
php artisan schedule:list
```

`queue:restart` إشارة خروج لطيف للعامل الموجود فقط، وليس إنشاء خدمة أو دليلًا على عودتها؛ تحقق من عودة العامل ونسخته فعليًا. يستدعي المجدول المعتمد `php artisan schedule:run` كل دقيقة، دون إضافة cron مكرر. راجع ظهور `announcements:notify-due` و`fcm:retry-pending` و`results:publish-due` و`student-exams:finalize-expired` والعمل الفعلي لها؛ تبقى مهام المكتبة والمالية القائمة.

7. تحقق من ملفات المكتبة والتخزين، ثم من القبول أدناه وسجل الأخطاء والطابور:

```bash
php artisan library:verify-files --fail-on-error
php artisan queue:failed
```

فشل تحقق ملف لا يأذن بحذفه أو حذف سجل صاحبه. بعد معالجة مشكلة طابور مؤكدة، يسمح مسار الاسترداد القائم بـ`php artisan fcm:retry-pending`؛ لا يعيد أحداثًا بلا payload ولا أحداثًا ملغاة. لا `queue:retry all`، ولا مسح جماعي لـ`queued_at` أو إيصالات الأجهزة. تُراجع أي مهمة فاشلة ويُعاد UUID المحدد فقط بعد التحقق من أهليتها الحالية.

## إعدادات التكامل وحدود الإلغاء

لا تحتاج الجولة أسماء أسرار جديدة. تبقى إعدادات `FIREBASE_PROJECT_ID` و`GOOGLE_APPLICATION_CREDENTIALS` للخادم، وإعدادات `VITE_FIREBASE_*` العامة وقت البناء، من مشروع واحد. لا يوضع مفتاح حساب الخدمة في VITE. قناة ولي الأمر Web Push/VAPID منفصلة عن FCM؛ مفاتيحها الخاصة تبقى سرية. يحتاج المساعد `GEMINI_API_KEY` والنموذج المعتمد الموجود في `GEMINI_MODEL`. عدم التهيئة يعرض حالة واضحة ويحفظ السؤال؛ لا يُعد ذلك تشغيلًا حيًا للمساعد.

أرشفة الإعلان توقف ظهوره وتلغي أحداث FCM المعلّقة وتحفظ سجل الإشعار. العامل يعيد فحص الإعلان والجمهور، كما يتحقق من نشر فترة النتيجة ومراجعتها ونتيجة الطالب وعلاقة الولي قبل إرسال إشعار نتيجة. **لا يمكن سحب رسالة قبلها المزود أو إيقاف اتصال إرسال تجاوز فحص الأهلية قبل الإلغاء.** لا تدّعي `sent_at` ظهور الإشعار على هاتف، ولا ضمان exactly-once بعد فقد رد مزود.

إعادة نشر إعلان مؤرشف قد تعيد ظهوره وفق سياسة العرض الحالية، لكنها لا تعيد إرسال حدث Push الملغى تلقائيًا. يبقى تاريخ الإلغاء محفوظًا. قناة VAPID المتزامنة لا ترث آلية outbox؛ الإرسال الجاري لا يمكن سحبه عبر الأرشفة.

## الرجوع دون فقد بيانات جديدة

رجوع الكود منفصل عن استعادة قاعدة البيانات. نسّق الكتابات والعمال والمجدول أولًا، ثم أعد المصدر والأصول والكاش المتطابقين وفق إجراء الاستضافة. لا تستعد نسخة قاعدة قديمة فوق إجابات ودرجات ورسائل ومدفوعات وملفات أضيفت بعد النسخة الاحتياطية؛ أي استعادة تحتاج خطة تسوية تحافظ عليها.

- **إلغاء FCM:** احتفظ بعمودي الإلغاء. `down()` يرفض إسقاطهما عند وجود أحداث ملغاة، ولا تتجاوز الحارس بحذف الأحداث. إبقاء الأعمدة وحده لا يجعل عامل الإصدار السابق آمنًا، لأنه قد يتجاهل الإلغاء. يجب الإبقاء على عامل متوافق يحترم `cancelled_at` وفحوص أهلية الإعلان/النتيجة، أو إبقاء التوصيل متوقفًا إلى أن تعتمد معالجة محددة للمهمات المعنية دون محو التاريخ. لا تشغّل عاملًا قديمًا على صف حالي دون هذا التحقق.
- **إيصالات حفظ الدرس:** احتفظ بجدول `lesson_save_requests`؛ إسقاطه يفقد معرفة الطلبات التي نجحت وقد تعاد بعد ضياع ردها. قد تكون لدى معلم صفحة مفتوحة تحتفظ بنفس الطلب والملفات لإعادة المحاولة. لا تمسح الإيصالات ولا تغير مفاتيح الطلب ولا تعالج العودة بإعادة رفع جماعي. يجب أن يبقى endpoint الحفظ متوافقًا مع إيصالات الجولة أثناء تصريف تلك المحاولات؛ العامل لا يعالج رفع الدرس، لذلك تحديث worker وحده لا يكفي.
- تبقى أعمدة outbox وملكية مساعد المعلم السابقة والملفات المشفرة وAPP_KEY محفوظة كذلك. لا down جماعي للترحيلات القديمة والجديدة، ولا حذف عمل طالب لتسهيل الرجوع.

فحص الجولة أثبت الترقية من الأساس المحدد والاستعادة على PostgreSQL محلي مع بيانات اصطناعية. لا يثبت إصدار قاعدة الاستضافة أو زمن الأقفال تحت حملها أو سرعة استعادة بياناتها. نتائج الاختبارات والأرقام والبصمات التفصيلية مرجعها تقرير القبول و`docs/qa/round-2/evidence/postgres-round-two-upgrade.json`.

## قائمة القبول بعد النشر

يستخدم المسؤول وQA **حسابات اختبار معتمدة فقط**، مع تسجيل الإصدار والوقت والمتصفح/النظام والجهاز والنتيجة. لا إشعارات تجريبية إلى الأسر الحقيقية.

1. دخول الإدارة والمعلم والطالب والولي، فتح صفحاتهم بلا 500، وفحص منع المستخدم الآخر من روابط السجلات والمرفقات المباشرة.
2. واجب بملف وملاحظة عربية متعددة الأسطر، ثم عرضهما للمعلم وتصحيح الواجب ووصول إشعاره الداخلي إلى الطالب والولي وفق السياسة القائمة.
3. اختبار بأسئلة مختلطة وتنسيق آمن، حفظ جواب وتسليم وتصحيح، استيراد إلى الفترة الصحيحة، مراجعة واعتماد ثم نشر. لا تظهر النتيجة قبل النشر؛ تكرار الحفظ/الاستيراد لا يكررها؛ تصحيح معتمد لاحق يحفظ أثره.
4. إعلان فوري وآخر بوقت المدرسة قبل/بعد الحد، والانتهاء وعزل الصف والجمهور. أرشف إعلانًا قبل بدء التوصيل وتحقق من اختفائه وعدم إرسال حدثه المعلّق. افصل هذا عن فحص الهاتف الخارجي.
5. إنشاء محادثة طالب ومعلم وإعادة فتحها. عند تهيئة Gemini، تجربة سؤال تعليمي عام بإذن مالك بيئة الاختبار؛ عند غيابه تظهر الحالة الصريحة دون جواب مصطنع أو 500.
6. اختبار صورة الطالب المحفوظة وإعادة فتحها، وبطاقة عدة طلاب بعربية صحيحة وصورة اختيارية، وفلاتر المعلمين والأولياء والجداول والمكتبة والمالية والإعلانات، وحفظ إسناد المشرف وإعادة قراءته.
7. حذف سجل اصطناعي غير مرتبط، وتعطيل/أرشفة سجل له تاريخ مع بقاء النتائج والحضور والرسائل والمالية. تعطيل تعريف رسم لا يمحو الالتزامات أو المدفوعات القائمة. لا حذف طالب حقيقي لإثبات حذف ولي.
8. رفع صورة وفيديو اصطناعيين في درس، قطع اتصال **عميل الاختبار** ثم إعادة نفس الطلب من الصفحة المحفوظة، والتحقق من نسخة واحدة وفتح/تشغيل المرفق للطالب المخوّل. لا يُدّعى رفع متقطع بالبايت: الملفات تعاد بأمان من نفس الطلب.
9. بعد تهيئة المزود، إذن الهاتف/رفضه، التطبيق المثبت عند الحاجة، الشاشة المغلقة، النقر، الخروج وتبديل الحساب، بحسابات اصطناعية وأجهزة موثقة. نجاح المتصفح المحاكى لا يثبت iPhone أو Android فعليًا.
10. بعد إعادة تشغيل الخدمات، تحقق من العامل والمجدول وfailed_jobs وأعمار أحداث outbox، وأغلق قبول الإنتاج فقط بالأدلة الفعلية. لا تنشر مفاتيح أو أسماء/درجات حقيقية أو رموز أجهزة أو محادثات في التقرير.

## رسالة مختصرة قابلة للتحويل

> يرجى نشر إصدار الجولة الثانية الخاص بـNasbia من جذر المستودع، باستخدام PR وcommit النهائيين في تقرير القبول، وفق `ROUND_2_HANDOFF_AR.md`. النشر يدوي ولم ينفذه Codex. احفظ القاعدة والملفات وAPP_KEY، وابنِ الأصول من القفل، ثم طبّق ترحيل إلغاء أحداث FCM وترحيل إيصالات حفظ الدروس بالترتيب، وجدّد caches وأعد العامل والمجدول المتوافقين. لا تحذف تاريخ النتائج أو الرسائل أو المدفوعات ولا تُسقط أعمدة الإلغاء/إيصالات إعادة المحاولة عند الرجوع. نفّذ قائمة القبول بحسابات اختبار معتمدة؛ Push وGemini والأجهزة والإنتاج تحتاج تحققًا فعليًا منفصلًا.
